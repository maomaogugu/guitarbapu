GuitarBapu 开发路线规划
========================

文档目的
--------
这份文档用于在更换 AI 编程助手或额度耗尽后，快速恢复项目上下文。每个阶段都应该独立实现、测试和提交，不要一次性重构整个项目。

一、项目目标
------------
GuitarBapu 是一款面向吉他手的桌面扒谱工具：导入歌曲或吉他录音，分析音符和节奏，推荐可演奏的琴弦/品位，生成可编辑的六线谱，并导出为常用格式。

长期能力：
- 从 MP3/WAV/FLAC 读取音频，并支持录音输入。
- 对单音旋律和多音吉他素材进行音高、节奏分析。
- 处理多个吉他轨道（主音、节奏、Solo）。
- 推荐合理指法，并尽可能识别推弦、滑弦、击弦/勾弦等技巧。
- 通过 GUI 编辑、试听、定位和导出 TAB。
- 使用音源分离模型只提取吉他轨道。

二、当前仓库状态（截至本规划生成时）
--------------------------------------
已存在的主要文件：
- src/audio/loader.py：Audio Loader，返回 AudioData，支持 MP3/WAV/FLAC。
- src/audio/analyzer.py：Phase 2 基础实现，使用 librosa.yin，返回逐帧 pitch_hz 和 Note 元组。
- src/music/note.py：Note 数据对象，包含 MIDI、开始时间、持续时间、力度，并支持频率转换。
- src/music/guitar.py：标准吉他基础模型。
- src/music/tab.py：TabEvent/Tablature 基础数据结构。
- src/gui/app.py：PyQt6 GUI 骨架。
- tests/test_smoke.py、tests/test_analyzer.py：基础导入和音高分析测试。

依赖：numpy、librosa、soundfile、sounddevice、music21、PyQt6、pytest。

注意：Audio Loader 属于已完成模块。后续阶段不要修改其公开行为；如需重采样、降噪或声道处理，应在新的 preprocessing 模块中完成。

三、总体数据流
--------------
音频文件/录音
  -> AudioData
  -> 预处理（采样率、声道、降噪、音源分离）
  -> Pitch/Rhythm Analysis
  -> Note / Chord / Timing 对象
  -> Fretboard Mapping（琴弦、品位、指法）
  -> Tablature
  -> GUI 编辑与试听
  -> MIDI / MusicXML / Guitar Pro / PDF 导出

模块边界原则：音频模块只产生分析结果，music 模块只表达音乐对象，TAB 模块只负责指板映射和排谱，GUI 不直接实现算法。

四、分阶段路线
--------------

Phase 0：项目基础架构（已完成）
目标：建立可导入的 src 包、配置、日志、GUI 入口和测试目录。
验收：python -m pytest 可运行，模块边界清晰。
后续只在需要时维护，不做大规模重构。

Phase 1：Audio Loader（已完成）
目标：将音频文件解码为统一的 AudioData：waveform、sample_rate、duration、channels。
已有实现：src/audio/loader.py。
验收：覆盖支持格式、文件不存在、采样率和 mono/stereo 行为的测试。
约束：后续分析器接收 AudioData，不直接依赖文件路径；不要把预处理逻辑塞回 loader.py。

Phase 2：Pitch Detection（基础版已完成，需增强）
已有能力：
- src/audio/analyzer.py 使用 librosa.yin 做单音逐帧音高检测。
- 静音/低能量帧过滤为 NaN。
- 频率量化为 MIDI，并合并连续帧为 Note。
- AudioAnalysis.notes 和 features["pitch_hz"] 可供后续模块使用。

建议增强顺序：
1. 用真实 WAV/吉他单音样本做集成测试，验证 A2、E3、A4 等音高误差。
2. 增加置信度/voiced 标记，区分低置信度帧和真正休止。
3. 增加音符去抖、最短时长和相邻同音合并参数。
4. 根据采样率检查 fmax、frame_length 和 hop_length，给出清晰错误信息。
5. 保留当前 Note 和 AudioAnalysis 接口，避免影响 Audio Loader。

建议文件：src/audio/analyzer.py、src/audio/preprocessor.py（后续）、tests/test_analyzer.py、tests/fixtures/。
阶段提交示例：feat: add basic monophonic pitch detection。

Phase 3：Guitar Fretboard Mapping（基础版已完成）
目标：把 Note.midi 映射为一个或多个可演奏位置（string、fret）。

本阶段已完成：
- Guitar 支持标准 E-A-D-G-B-E 调弦、品位范围和 capo。
- src/music/fretboard.py 提供 FretPosition、所有位置枚举和 MIDI 查询。
- 提供优先低品位、减少换把和保持连续性的基础启发式选择。
- 已添加空弦、12 品、多位置、不可演奏音符、capo 和连续旋律测试。

当前限制：指法评分仍是启发式规则，暂不处理手指编号、和弦按法、滑弦/推弦等技巧。

实现顺序：
1. 完善 Guitar：弦数量、每根弦空弦 MIDI、品数、调弦方式。
2. 新建 src/music/fretboard.py，生成每根弦每个品位的 MIDI 索引。
3. 实现 find_positions(note) -> tuple[FretPosition, ...]。
4. 处理不可演奏音符、变调/降调调弦和 capo 参数。
5. 新建指法评分器：优先低品位，其次减少跨弦和换把，最后考虑连续音符的手指移动。

建议对象：FretPosition、FingeringCandidate、FingeringCost。不要让 TAB 渲染代码直接计算 MIDI。
测试：覆盖标准调弦空弦、12 品八度、音符多位置、超出指板范围、连续旋律评分。
阶段提交示例：feat: map notes to guitar fretboard positions。

Phase 4：Timing 与 Note 清理（已完成）
目标：把逐帧检测结果变成稳定、可编辑的节奏事件，为 TAB 排版做准备。

本阶段已完成：
- 新增 NoteProcessor，支持 0.08 秒最短时长、短间隔同音合并、夹心抖动删除和单音重叠处理。
- 使用 librosa 检测 onset 和 tempo；失败时保留秒级时间，不影响音高结果。
- 新增 TimingInfo、QuantizedNote 和 Rest，默认量化到每拍四等分网格。
- 保留 raw_notes、原始秒级时间、频率和基础置信度，量化结果不会覆盖来源数据。
- 同音重复由可靠 onset 分割；跨小节事件支持 tie_to_next 标记。
- GUI 已改为后台分析，并显示清理统计、BPM、拍位置、时值、休止段和置信度。
- 真实 60 秒六弦调音录音由 70 个原始事件清理为 30 个正确事件，E2/A2/D3/G3/B3/E4 各 5 次。

当前限制：自动拍号识别尚未实现，tempo 可能存在半拍/双拍歧义；完整和弦与复音不属于本阶段。

实现顺序：
1. 增加 onset/offset 检测，去掉 YIN 首尾边缘误检。
2. 增加节拍估计和拍号/tempo 数据对象；未知 tempo 时仍保留秒级时间。
3. 将音符时值量化为可配置网格（如 1/16、1/8），保留原始时间用于回溯。
4. 明确休止符、连音、重叠音符和同音重复的规则。
5. 为 Note 增加可选 confidence、原始频率等分析元数据，但保持 midi/start/duration 兼容。

建议文件：src/music/timing.py、src/audio/rhythm.py、src/music/note.py。
测试：合成节拍音频、已知 BPM 的短旋律、边界帧、静音段和量化误差。
阶段提交示例：feat: normalize detected note timing。

Phase 5：TAB Generator（已完成）
目标：将音符和指法位置转换为结构化、可编辑的六线谱。

本阶段已完成：
- 扩展 TabEvent/Tablature，保存 Note、琴弦、品位、秒级时间、拍位置、时值、小节、延音、置信度和技巧字段。
- 新增 FingeringOptimizer，以动态规划全局优化低品位、换把、跨弦和大跨度成本。
- 支持同一拍多个结构化音符分配到不同琴弦；当前分析器仍保持单音能力。
- 新增 TabGenerator，处理默认 4/4、小节、休止符、跨小节延音和无法映射音符。
- 新增 TextTabRenderer，支持一位/两位品位对齐、每行四小节、长 TAB 换行和 `x` 警告。
- GUI 已显示真正的六线谱，并在下方保留音符详情。
- 真实六弦调音 WAV 生成 30 个 TAB 事件、0 个未映射；六根弦各有 5 次正确空弦。

当前限制：Phase 7 已提供 TAB 事件编辑和文件导出，但技巧字段仍需人工填写，尚未自动识别；复音和弦识别仍属于后续模型能力。

实现顺序：
1. 扩展 TabEvent/Tablature，保存音符关联、弦、品、时间和技巧。
2. 对一段 Note 序列调用指法优化器，得到稳定的连续位置。
3. 支持休止、和弦（同一时间多个事件）、小节线和拍号。
4. 实现文本 TAB 渲染器，先保证确定性和可测试性。
5. 为 GUI 提供结构化数据，不让 GUI 解析文本 TAB。

验收示例：E4-G4-A4 能生成合法六线谱；每个事件弦号和品位在吉他范围内；无法映射时给出诊断而不是静默丢失。
测试：单音阶、跨弦替代位置、和弦、不可映射音符、换把成本。
阶段提交示例：feat: generate editable guitar tablature。

Phase 6：导出与持久化（已完成）
目标：让分析结果可以保存、交换和在外部软件打开。

本阶段已完成：
- 新增 TranscriptionProject 和版本 1 JSON 项目格式，保存音频引用、分析参数、Note、TimingInfo、RhythmAnalysis、Guitar 和完整 Tablature。
- 项目文件使用相对音频路径，不嵌入波形或逐帧 pitch_hz；原音频缺失时仍可打开和查看 TAB。
- 新增文本 TAB 导出，内容与 GUI 的 TextTabRenderer 保持一致。
- 使用 music21 实现 MIDI 和 MusicXML 导出，保留音高、力度、拍位置、时值、BPM 和拍号。
- MusicXML 写入琴弦和品位技术标记；MIDI 保留通用音乐事件，但不表达文本 TAB 排版。
- GUI 新增打开项目、保存项目、导出 TAB、导出 MIDI 和导出 MusicXML 操作，只有存在分析结果时才启用。
- 增加 JSON round-trip、未知版本、音频缺失、TXT 快照、MIDI/MusicXML 读取和 GUI 工作流测试。

当前限制：PDF 和 Guitar Pro 原生导出尚未实现；项目文件不包含音频，音频移动后不能直接播放或重新分析；当前 MIDI/MusicXML 内容质量仍受单音检测和节奏估计准确度限制。

实现顺序：
1. 先实现 JSON 项目文件，保存音频引用、Note、Tablature、调弦和分析参数。
2. 使用 music21 生成 MIDI/MusicXML，并核对 tempo、时值和音高。
3. 评估 Guitar Pro 导出方案（优先使用稳定库或 MusicXML 中间格式）。
4. 增加 PDF/文本 TAB 导出，明确字体和分页策略。
5. 为每种导出格式增加 round-trip 或内容快照测试。

建议文件：src/export/json.py、src/export/midi.py、src/export/musicxml.py、src/export/guitarpro.py、src/project/model.py。
阶段提交示例：feat: export transcription to midi and project json。

Phase 7：GUI 工作流（已完成）
目标：提供可用的导入、分析、查看、编辑和导出流程。

本阶段已完成：
- 使用 Qt Multimedia 增加播放、暂停、停止、时间滑块和毫秒级时间显示。
- 新增无第三方依赖的 WaveformWidget，显示音频包络、播放游标、音符位置，并支持点击定位和拖动循环选区。
- 选择 TAB 事件会定位音频并选中对应播放区间；可循环播放波形选区或单个事件。
- 新增独立 TabEditController，以不可变 Tablature 快照实现插入、编辑、删除、撤销、重做和项目脏状态。
- 修改 MIDI 时自动选择接近当前位置的合法指法；位置选择只列出该音高的合法琴弦/品位，防止 TAB 与音高不一致。
- 插入或移动事件时检测同一琴弦的时间重叠；自动指法会优先尝试其他可用琴弦。
- 支持编辑开始拍、音符时值和技巧标签，并自动更新秒级时间、小节、跨小节延音和小节总数。
- 新增事件编辑对话框和结构化事件表；项目保存与全部导出均使用编辑后的 Tablature。
- 打开带有有效音频引用的项目会恢复波形和播放；音频缺失时仍可编辑、保存和导出。
- 增加后台分析忙碌状态和安全取消；离开未保存修改时提供保存、放弃和取消选项。
- 增加控制器、波形、事件对话框、GUI 编辑、取消和未保存提示测试。

当前限制：取消分析无法中断正在执行的 librosa.yin 内部计算，只会丢弃完成结果；循环选区为单一区间，尚不支持多个练习标记；编辑后的 Tablature 是最终输出，AudioAnalysis.notes 保留为原始算法结果；真实复音歌曲仍受单音检测能力限制。

实现顺序：
1. 文件选择和音频元数据显示。
2. 开始/取消分析、后台线程和进度/错误状态。
3. 音频波形与时间游标；点击音符可定位播放。
4. TAB 编辑：修改音符、弦、品、时值和删除/插入事件。
5. 播放、暂停、循环选区和导出按钮。
6. GUI 只调用 AudioAnalyzer、Fretboard、Tablature 和 export API。

测试：优先测试无 GUI 的 controller/service；再做关键 Qt 界面 smoke test。任何耗时分析不得阻塞主线程。
阶段提交示例：feat: add end-to-end transcription gui workflow。

Phase 8：音源分离与多轨分析（基础版已完成）
目标：从完整歌曲中提取吉他轨，再进行音高和节奏分析。

本阶段已完成：
- 新建可替换的 Separator 接口、Stem/SeparationResult 数据对象和进度/取消契约。
- 接入可选 Demucs `htdemucs_6s`，只使用模型真实提供的 `guitar` stem，绝不用 `other` 冒充吉他。
- 实现基于音频内容和模型配置的 SHA-256 缓存，使用临时目录和原子提交，结果放在仓库外。
- 新建 TranscriptionService，编排“可选分离 -> 既有 Loader -> Analyzer -> TAB Generator”，未改变 Audio Loader 公开行为。
- GUI 可选“先分离吉他”，显示模型/设备/进度/缓存命中，并在原音频和吉他分离轨之间切换播放。
- 项目保存仍引用原音频，额外记录分离缓存键；缓存存在时可在打开项目后恢复 stem 播放。
- 基础安装仍不包含 PyTorch/Demucs，可通过 requirements-separation.txt 选择安装。

当前限制：CPU 分离完整歌曲可能较慢；stem 可能有泄漏和伪影；尚未拆分主音/节奏吉他；分离后仍需选择单音或实验性复音分析。多 stem 数据结构已预留，但不自动合并冲突事件。

阶段提交示例：feat: add optional guitar stem separation。

Phase 9：高级识别与产品化
目标：提升真实歌曲可用性，而不是继续堆叠未经验证的算法。

已完成 Phase 9A 基础版：
- 新增 Chord 数据对象，保存具体 MIDI 音高、时间、根音、和弦类型和可信度。
- 新增独立 PolyphonicAudioAnalyzer，使用 CQT、onset 分段、能量阈值和泛音抑制同时检测最多 6 个吉他音高。
- 支持 major、minor、power、sus2、sus4、diminished 和 augmented 基础标签。
- 将同时音符交给现有 TAB/FingeringOptimizer，并限制候选和弦指法数以避免组合爆炸。
- GUI 可切换“单音（推荐）/和弦复音（实验）”，可与 Demucs 吉他分离组合使用。
- 项目文件保存和弦结果，并向后兼容没有 chords 字段的旧项目。
- 基础复音识别只使用已有 librosa，未强制增加大型模型。

当前 Phase 9A 限制：快速闷音、强失真、密集混音和泛音可能误检；根音/转位存在听觉歧义；尚不支持复杂扩展和弦。所有结果仍需试听和人工修正。

已完成 Phase 9B 基础版：
- 新增 TrackRole、TrackCandidate 和 TranscriptionTrack，支持 lead、rhythm、unknown 和人工 Solo 角色。
- 新增 TrackClassifier，将单音段分入主音候选、同时音/和弦分入节奏候选、低可信度事件分入未分类。
- 每个检测音符只进入一条逻辑轨，不在主音/节奏轨之间重复。
- TranscriptionService 会为每条逻轨独立生成 Analysis 和 Tablature，但保留完整分析快照兼容旧接口。
- 项目格式可选保存 tracks/active_track_id，旧单轨项目仍可正常打开。
- GUI 可切换逻轨、查看来源/可信度、手动改角色，并为每条轨独立保留 TAB 编辑、撤销/重做和导出。
- 导出只针对当前选中轨道，不自动合并冲突轨道。

当前 Phase 9B 限制：轨道共享同一原音频或综合 guitar stem，并不对应独立 lead/rhythm WAV；主音与节奏同时演奏时无法从通用 Demucs guitar stem 中完全分开；Solo 角色尚需人工指定。

已完成 Phase 9C 基础版：
- 新增 GuitarTechnique 和 TechniqueDetection，分别保存技巧类型、目标音符、关联音符、音高变化和独立可信度。
- 新增独立 TechniqueAnalyzer，使用 YIN 连续音高、RMS 振幅起音和周期调制特征，不依赖新的大型模型。
- 支持 slide、hammer-on、pull-off、bend 和 vibrato 五种保守候选；复音区段和证据不足时保持未分类。
- TranscriptionService 在原音频或 Demucs guitar stem 上运行技巧检测，再交给现有 TAB 和逻辑多轨流程。
- AudioAnalysis、逻辑轨、TabEvent 和项目 JSON 可保存技巧结果；旧项目缺少新字段时仍兼容。
- GUI 显示自动技巧及独立可信度，用户修改标签后会清除自动可信度。
- 文本 TAB 输出技巧候选清单，MusicXML 保留可读技巧文字；MIDI 不承诺保存吉他技巧。
- 添加纯特征、真实 librosa 合成音频、TAB 映射、项目持久化、GUI、编辑和导出测试。

当前 Phase 9C 限制：只自动处理单音区段，每个音符只保留一个主要技巧；不识别组合技巧、预推弦、推弦释放或精确推弦目标；强失真、混响和混音泄漏可能误检。所有自动标签必须试听确认。

已完成 Phase 9D 基础版：
- 新增跨平台用户数据、缓存、日志和崩溃报告路径策略。
- 新增滚动日志和主线程/后台线程未捕获异常报告。
- 新增只读系统诊断，可检查核心依赖、可选 Demucs 依赖、模型缓存和目录状态。
- 新增显式 Demucs 模型管理；仅用户确认后下载 `htdemucs_6s` 权重，不把模型或缓存写入 Git。
- GUI 帮助菜单提供系统诊断、模型准备和日志目录入口；模型准备在后台执行。
- 新增 `pyproject.toml`、开发依赖、macOS/Linux/Windows 启动脚本和 PyInstaller 基础/Full 包配置。
- 添加产品化基础设施、模型状态、诊断、GUI 菜单和脚本测试。

当前 Phase 9D 限制：当前环境未完成签名、公证、安装器和自动更新；PyInstaller 需要在目标操作系统、目标 Python 版本上分别构建；Full 包体积较大，Demucs 权重仍建议首次运行时单独下载。

后续方向：
- 用真实和弦素材评估复音音高，再决定是否接入预训练模型。
- 用有标签真实素材评估技巧候选，再决定是否接入专用轻量模型。
- 人工修正反馈和 AI 辅助重排指法。
- 结果置信度、可解释的错误提示和批量处理。
- 安装包、模型下载、日志诊断、跨平台打包。

每项高级功能都先定义数据格式、评测指标和失败回退策略，再实现模型；低置信度结果必须允许用户编辑。

五、每个阶段的固定执行模板
--------------------------
1. 阅读当前相关模块和测试，不修改无关文件。
2. 写清输入/输出数据契约和不支持的情况。
3. 先添加失败测试，再实现最小功能。
4. 保持模块化，避免把逻辑放入 GUI 或 main 入口。
5. 运行 python -m pytest、python -m compileall -q src tests、git diff --check。
6. 更新 README 和本路线文档中的状态。
7. 提交一个单一目的的 commit，并记录变更文件、测试命令和已知限制。

六、推荐的下一步
----------------
当前最合理的下一步是验证 Phase 9D，然后进入发布工程。推荐顺序：

1. 准备带技巧标签的自有/授权干净 DI 吉他素材，分别覆盖滑弦、击弦、勾弦、推弦、颤音和普通拨弦负样本。
2. 记录每类技巧的精确率、召回率、误检片段、音高区间、速度和失真条件，不只观察单个演示音频。
3. 在三种操作系统分别构建并实测基础包和 Full 包，确认音频设备、模型缓存、日志目录和导出权限。
4. 完成签名、公证、安装器、版本发布和自动更新，再考虑专用轻量技巧模型。

当前不要做：把未签名构建直接当作正式发行版、把 Demucs 强制加入基础安装、把模型权重提交到 Git、用少量合成音频宣称高准确率、把低可信度技巧强制写入最终谱，或一次性重写已经稳定的 Loader、分析、TAB 和 GUI 数据契约。
